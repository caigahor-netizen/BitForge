串口收到一帧数据、从 Flash 读出一段参数，怎样判断数据是否在传输或存储过程中发生了变化？CRC 就是常见的检查方法。

**CRC-8、CRC-16、CRC-32 中的数字，表示校验结果的位数，分别占 1、2、4 字节。它们不表示一次只能校验 8、16、32 位数据，也不表示 CPU 必须具有对应位宽。**

## 1. CRC 在检查什么？

CRC 是 Cyclic Redundancy Check，即循环冗余校验。发送方按照约定的算法计算数据的 CRC，把结果附在数据后面；接收方对收到的数据重新计算，再与收到的 CRC 比较。

```text
发送方：数据 ──计算 CRC──→ [ 数据 | CRC ]
                                │ 传输
接收方：收到的数据 ──计算 CRC──→ 与收到的 CRC 比较
                                ├─ 不同：校验失败
                                └─ 相同：校验通过，仍有漏检可能
```

它主要检测随机传输错误和存储损坏。CRC 通常不能指出哪一位错了，也不能直接纠正错误；发生错误后，可以由上层协议决定丢弃、重传或报错。

**CRC 不是加密或身份认证。**攻击者可以修改数据后重新计算 CRC。固件防篡改需要数字签名等机制，不能只检查 CRC。

## 2. 原理：把数据当作多项式，求除法余数

先看普通除法：除数固定时，不同数字可能得到相同余数。因此，余数可以帮助检查变化，却不能唯一代表原始数据。CRC 也使用“余数”，但做的是二进制多项式除法。

例如，二进制 `1101` 对应：

```text
1 × x³ + 1 × x² + 0 × x + 1 = x³ + x² + 1
```

这里系数只有 0 和 1，运算在 GF(2) 上进行。可以先记住最有用的一点：**加法和减法都是异或 XOR，不进位，也不借位。**

```text
0 XOR 0 = 0    0 XOR 1 = 1
1 XOR 0 = 1    1 XOR 1 = 0

1101 XOR 1011 = 0110
```

对于宽度为 `w` 的基础 CRC 模型：

1. 选定一个最高次数为 `w` 的生成多项式 `G(x)`。
2. 在原始数据末尾补 `w` 个 0，相当于乘以 `x^w`。
3. 用 `G(x)` 做模 2 除法，得到不足 `w + 1` 位的余数。
4. 将余数写成固定 `w` 位，作为 CRC 附到原始数据后面。

这样构造出的完整码字能被 `G(x)` 整除。接收时，若错误模式也恰好是 `G(x)` 的倍数，错误就会漏检；否则能检测到变化。这也解释了为什么**多项式的选择会影响检错能力**。

## 3. 用一个 3 位 CRC 手算一遍

为了看清计算过程，暂时不用 8 位或 16 位，而使用教学用的 3 位 CRC：数据为 `1101`，生成多项式为 `1011`，即 `x³ + x + 1`，初值为 0，无反射、无最终异或。

先在数据后补 3 个 0：

```text
1101 → 1101000
```

把除数最高位对齐当前余数的最高位为 1 的位置，反复异或：

```text
  1101000
⊕ 1011000
---------
  0110000
⊕ 0101100
---------
  0011100
⊕ 0010110
---------
  0001010
⊕ 0001011
---------
  0000001
```

余数是 `001`，所以发送的数据与 CRC 拼接为 `1101001`。对 `1101001` 用相同除数做模 2 除法，余数为 0。

这里说明的是基础数学模型。实际协议常增加非零初值、输入/输出反射和最终异或，不能把所有 CRC 都理解成“直接计算整帧，结果一定为 0”。有些模型具有规定的固定余数（residue），必须连同 CRC 字段编码方式一起核对。

## 4. CRC-8、CRC-16、CRC-32 的区别

| 比较项 | CRC-8 | CRC-16 | CRC-32 |
| --- | --- | --- | --- |
| 校验结果宽度 | 8 位 | 16 位 | 32 位 |
| 附加字段大小 | 1 字节 | 2 字节 | 4 字节 |
| 可能的结果数量 | 256 | 65,536 | 4,294,967,296 |
| 可保证检测的突发错误长度上限* | 8 位 | 16 位 | 32 位 |
| 随机错误漏检概率的常用近似** | 1/256，约 0.39% | 1/65,536，约 0.0015% | 1/4,294,967,296，约 0.000000023% |
| 应用例子 | SMBus 的 PEC | Modbus RTU | gzip 数据完整性检查 |

\* 对最高次数为 `w`、常数项为 1 的标准生成多项式，能检测所有长度不超过 `w` 位的突发错误。突发长度指**从第一个错误位到最后一个错误位的跨度**，中间不要求每一位都出错；前提是码字长度和帧边界保持不变。

\** `2^-w` 是错误综合近似均匀分布时的估计，不是任意干扰下的固定漏检率，更不是设备总故障概率。短突发错误可能保证检出，而某些特定错误模式可能必然漏检。比较实际可靠性时，还必须考虑多项式、帧长和错误模型。

**CRC-32 不等于能检测任意 32 个错误位。**32 个错误位可能分散在很长的一帧里，与“长度不超过 32 位的突发错误”是两回事。对特定位数错误的保证，还要看给定帧长下的最小汉明距离；最小汉明距离为 `d` 时，能保证检测最多 `d - 1` 个翻转位。

这些应用采用的具体 CRC 定义可分别查阅 [SMBus 官方 FAQ](https://smbus.org/faq/faq_main.htm)、[Modbus 串行链路规范](https://www.modbus.org/file/secure/modbusoverserial.pdf)和 [RFC 1952 的 gzip 规范](https://www.rfc-editor.org/rfc/rfc1952.html)。

## 5. 同样叫 CRC-16，为什么算出来不一样？

因为“CRC-16”只说明位宽，**还没有完整指定算法**。双方至少要统一以下参数：

| 参数 | 含义 |
| --- | --- |
| `width` | CRC 的位宽 |
| `poly` | 生成多项式，通常省略必定为 1 的最高次项 |
| `init` | 开始处理数据前的寄存器初值 |
| `refin` | 是否反射每个输入字节的位顺序 |
| `refout` | 是否按模型约定反射输出寄存器 |
| `xorout` | 输出 CRC 前异或的常数 |

例如，`x⁸ + x² + x + 1` 的完整二进制表示是 `1 0000 0111`，写成十六进制为 `0x107`。CRC-8 参数中的 `poly` 通常写为 `0x07`，省略了 `x⁸` 项。

下面列出三种**明确命名的变体**，并附上 ASCII 字符串 `123456789` 的校验结果。测试输入不包含结尾的 `\0` 或换行。

| 算法 | poly（正常表示） | init | refin / refout | xorout | 测试结果 |
| --- | --- | --- | --- | --- | --- |
| CRC-8/SMBUS | `0x07` | `0x00` | false / false | `0x00` | `0xF4` |
| CRC-16/MODBUS | `0x8005` | `0xFFFF` | true / true | `0x0000` | `0x4B37` |
| CRC-32/ISO-HDLC | `0x04C11DB7` | `0xFFFFFFFF` | true / true | `0xFFFFFFFF` | `0xCBF43926` |

反射是位顺序转换，例如 8 位的 `00000110` 反射后为 `01100000`。实现中常把反射融入右移计算，因此不能看到 `refout=true` 就在任何代码末尾再反射一次。

正常表示的 `0x8005` 在常见的反射右移实现中对应 `0xA001`；`0x04C11DB7` 对应 `0xEDB88320`。它们是同一多项式在不同位序实现中的表示，不能随意互换移位方向和常量。

另外，CRC-32C 使用不同的生成多项式，不等同于表中的 CRC-32/ISO-HDLC。仅凭名称里都有“32”，无法判断它们能否互通。

## 6. 一个可直接理解的 Modbus CRC-16 实现

下面采用逐位右移算法。每次先把一个字节异或到 CRC 的低 8 位，再进行 8 次移位与条件异或。

```c
#include <stddef.h>
#include <stdint.h>

uint16_t crc16_modbus(const uint8_t *data, size_t len)
{
    uint16_t crc = 0xFFFFu;

    for (size_t i = 0; i < len; ++i) {
        crc ^= data[i];

        for (unsigned int bit = 0; bit < 8; ++bit) {
            if (crc & 1u) {
                crc = (uint16_t)((crc >> 1) ^ 0xA001u);
            } else {
                crc = (uint16_t)(crc >> 1);
            }
        }
    }

    return crc;
}
```

测试与组帧示例：

```c
const uint8_t test[] = "123456789";
uint16_t check = crc16_modbus(test, sizeof(test) - 1);
// check 应为 0x4B37，不能把字符串末尾的 '\0' 算进去。

uint8_t frame[8] = {0x01, 0x03, 0x00, 0x00, 0x00, 0x0A};
uint16_t crc = crc16_modbus(frame, 6);
// crc 应为 0xCDC5。
frame[6] = (uint8_t)(crc & 0xFFu);
frame[7] = (uint8_t)(crc >> 8);
// 完整帧：01 03 00 00 00 0A C5 CD
```

Modbus RTU 规定 CRC **低字节先发，高字节后发**。因此数值 `0xCDC5` 在帧中写成 `C5 CD`。CRC 内部的位反射与最终两个字节的发送顺序是不同问题；应使用显式移位提取字节，不依赖 CPU 内存端序。[Modbus 规范：CRC 计算与传输顺序](https://www.modbus.org/file/secure/modbusoverserial.pdf)

上面的实现已包含该模型需要的处理，**调用前不用在数据后额外补两个零字节**。数学推导中的补零步骤，已经通过这种常见的寄存器算法实现；再补零会算出另一段输入的 CRC。

## 7. 工程里怎样选择和排查？

已有协议时，直接遵守协议规定的变体、覆盖范围和字段顺序。不能为了“更可靠”就把 Modbus 的 CRC-16 单方面换成 CRC-32，否则对端无法识别。

设计自定义协议时，可以从帧长、允许的漏检风险、传输开销及硬件支持入手：短控制报文可评估 CRC-8 或 CRC-16，较大数据块可评估 CRC-32，但最终需要验证具体多项式在目标帧长下的检错能力，不能只按位宽拍板。Philip Koopman 的研究表按位宽、数据长度和汉明距离列出了多项式性能，并说明了适用的错误模型。[CMU：CRC 多项式选择与汉明距离表](https://users.ece.cmu.edu/~koopman/crc/)

CRC-32 的计算时间也不一定是 CRC-8 的四倍。逐位算法通常每字节循环 8 次；查表算法用存储空间换速度；硬件 CRC 外设还能进一步加速。实际性能取决于 CPU、实现方式和数据访问开销。

如果软件与硬件算出的结果不一致，按下面顺序检查：

1. **输入字节是否相同。**十六进制字节 `01 03` 与文本字符串 `"0103"` 完全不同；字符串终止符、换行和结构体填充字节也会改变结果。
2. **覆盖范围是否相同。**地址、命令、长度、数据字段是否参与校验，要以协议为准。重新计算并比较时通常不包含收到的 CRC 字段。
3. **参数是否一致。**核对多项式、初值、反射和最终异或，不要只核对“都是 CRC-16”。
4. **喂入顺序是否一致。**硬件按字或字节处理数据时，需核对字节顺序、末尾不足一个字的数据如何处理，以及是否引入了补齐字节。
5. **状态是否正确初始化。**新帧需要重置初值；同一帧分块计算时，应正确延续中间寄存器状态，而不是每块重新开始。
6. **CRC 字段的收发顺序是否一致。**先核对数值，再核对字段里的字节排列。

调试时先让 `123456789` 通过，再验证协议样例和实际报文。一个标准向量只能发现部分错误，还应覆盖空输入、含 `0x00`/`0x80`/`0xFF` 的数据以及非整字长输入，尤其是软件与硬件实现互相对照时。

理解 CRC 最关键的是把三个问题分开：**数学上怎样求余数、协议选了哪组参数、线上究竟校验和发送哪些字节。**8、16、32 决定结果宽度；完整参数与报文约定决定双方能否算出同一个结果。
