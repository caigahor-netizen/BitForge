用 Keil 编译 STM32 工程后，会生成一个 `.bin` 文件。用文本编辑器打开它，通常只能看到乱码；但下载器把它写入芯片后，单片机就能执行程序。这些看似杂乱的字节，究竟是什么？

这篇文章以实际的 `myBalanceCar.bin` 为例，拆解其中的向量表、机器代码、字符串、OLED 字库，以及变量的初始值。

本文直接检查了 BIN 的字节，并参考同目录的 `myBalanceCar.map`、`myBalanceCar.hex`、工程配置和启动文件。HEX 数据的校验和全部通过，其 16,392 字节数据与 BIN 逐字节一致；MAP 中的镜像大小、复位入口、栈顶及初始化数据布局也与 BIN 对应。函数名和变量名来自这些辅助文件，不能误认为是从裸 BIN 中直接读出的名称。本文没有在硬件上运行固件，也没有完整还原控制逻辑。

**BIN 是将要装入存储器的一串字节。**

本次分析的 `myBalanceCar.bin` 大小为 **16,392 字节，即 0x4008 字节，约 16.01 KiB**。工程配置指定的目标器件是 `STM32F103C8`，内核为 Cortex-M3。

这里的 BIN 是平坦二进制镜像。它没有像 ELF 那样的标准节表和符号表，下载地址需要由工具配置等外部信息提供。Arm 的 fromelf 可以生成这种 plain binary 输出。[Arm fromelf 文档](https://support.arm.com/documentation/dui0805/b/fromelf-command-reference/--bincombined?lang=en)

本文件通过 HEX 和 MAP 核对得到的装载起点为 `0x08000000`，因此：

```text
Flash 地址 = 0x08000000 + BIN 内的字节偏移

文件偏移 0x00000000 → Flash 地址 0x08000000
文件偏移 0x00000188 → Flash 地址 0x08000188
文件偏移 0x00004007 → Flash 地址 0x08004007
```

“文件偏移”表示从文件开头数了多少字节，“Flash 地址”表示这些字节烧录后在芯片存储器中的位置。两者不要混淆。也不能把这个地址公式直接套给所有 BIN：其他工程可能使用 Bootloader、不同链接地址或多装载区域。

**文件开头不是第一条指令，而是一张入口表。**

这个 BIN 的前 16 个字节是：

```text
文件偏移    原始字节
0x0000      B0 0D 00 20
0x0004      89 01 00 08
0x0008      93 27 00 08
0x000C      31 21 00 08
```

按照该固件使用的小端序，每四个字节解释为一个 32 位数。小端序就是低位字节先放：`B0 0D 00 20` 对应数值 `0x20000DB0`。

| 文件偏移 | 32 位数值 | 含义 |
|---|---|---|
| `0x0000` | `0x20000DB0` | 初始主栈指针 MSP |
| `0x0004` | `0x08000189` | 复位处理函数入口，带 Thumb 标记 |
| `0x0008` | `0x08002793` | NMI 处理函数入口 |
| `0x000C` | `0x08002131` | HardFault 处理函数入口 |
| `0x003C` | `0x08002C4D` | SysTick 处理函数入口 |

Cortex-M3 的向量表首先存储初始栈指针，随后存储复位及其他异常处理程序的入口。入口值最低位为 1，表示 Thumb 状态，所以复位向量 `0x08000189` 对应的实际指令地址是 `0x08000188`，不是从奇数地址取指。[ST Cortex-M3 编程手册 PM0056](https://www.st.com/resource/en/programming_manual/pm0056-stm32f10xxx20xxx21xxxl1xxxx-cortexm3-programming-manual-stmicroelectronics.pdf)

本工程的向量表占 `0xEC` 字节，也就是 236 字节。后面才开始出现启动代码和其他程序内容。很多外设向量重复指向 `0x080001A3`，与启动文件提供公共默认处理入口的做法对应，并不意味着每个外设都在运行。

栈顶 `0x20000DB0` 是 RAM 地址。MAP 显示，本工程为栈预留了 1,024 字节，范围为 `0x200009B0` 至 `0x20000DAF`，其上边界正好是初始栈顶。**栈顶位置不能用来推断芯片的全部 RAM 容量。**

**文件中间主要是机器代码，但代码附近也会夹着数据。**

你写下的 C 语言会经过编译和链接，变成处理器能够执行的机器指令。例如一次 GPIO 输出操作，会被实现为寄存器读写等指令；一次函数调用，会变成跳转与必要的现场保存操作。

MAP 中可以找到这个固件的几个入口：

| 函数 | 实际指令地址，已去掉 Thumb 标记 | 用途 |
|---|---|---|
| `Reset_Handler` | `0x08000188` | 复位后的启动入口 |
| `OLED_Clear` | `0x08002794` | OLED 清屏相关处理 |
| `SystemInit` | `0x08002CAE` | 系统初始化入口 |
| `USART1_IRQHandler` | `0x08003130` | USART1 中断处理 |
| `main` | `0x0800316C` | 用户主程序入口 |

这些名字来自 MAP 的符号信息。BIN 本身保存的是对应的指令字节，一般不保留 `main`、`OLED_Clear` 这样的函数名。

启动文件显示，复位处理会进入 `SystemInit`，再转交 C 运行库入口 `__main`，最终进入用户的 `main`。注意 `__main` 与 `main` 是不同的入口。本次链接中 `SystemInit` 的函数大小只有 2 字节，不能仅根据名字就说它完成了全部时钟配置。

反汇编也不能简单理解为“把每两个字节翻译成一条指令”。Thumb 指令有不同长度，代码区域内还可能包含常量池、字符串和对齐填充。把数据强行按指令解释，也可能得到看似正常、实际没有意义的汇编文本。

**BIN 中确实能读到文字。**

直接扫描原始字节，可以找到以下 ASCII 字符串：

| 文件偏移 | 对应 Flash 地址 | 可读内容 |
|---|---|---|
| `0x32A4` | `0x080032A4` | `SAVE:ERROR` |
| `0x32B0` | `0x080032B0` | `CHIP UID (96 bit)` |
| `0x32C4` | `0x080032C4` | `Hello World!` |
| `0x32DB` | `0x080032DB` | ` SAVE:OK`，带一个前导空格 |

它们提示固件中包含保存结果、芯片 UID 和问候语相关的文本。不过，发现字符串并不能独立证明相应功能实际被执行，也不能确定它们显示在 OLED 上还是通过串口输出；这些需要沿着代码引用继续检查。

`CHIP UID (96 bit)` 只是文字标签，不是芯片的真实 UID 数值。类似地，文件名虽然叫 `myBalanceCar.bin`，也不能仅凭这个名字断言固件已实现平衡控制或某种 PID 算法。

**OLED 字库也是固件的一部分，而且占了约五分之一。**

这个 BIN 中有三组与 OLED 显示有关的只读数据，MAP 给出了它们的名字和大小：

| 数据对象 | 文件偏移范围，含两端 | 大小 |
|---|---|---:|
| `OLED_F8x16` | `0x32E4`～`0x38D3` | 1,520 字节 |
| `OLED_F6x8` | `0x38D4`～`0x3B0D` | 570 字节 |
| `OLED_CF16x16` | `0x3B0E`～`0x3FAD` | 1,184 字节 |
| 合计 | `0x32E4`～`0x3FAD` | **3,274 字节** |

合计约占整个 BIN 的 **20.0%**。因此，16 KiB 左右的固件并不代表其中全是控制算法或机器指令。

点阵字库保存的是像素图案。例如一个 8×16 的单色字符共有 128 个像素，单纯按每像素 1 位存储，需要 16 字节。显示函数读取这些数据，再根据屏幕要求组织和传输像素。具体字节对应行还是列、位序如何排列，要由字库格式和驱动代码共同决定。

这里 `OLED_F8x16` 的 1,520 字节恰好等于 95×16，`OLED_F6x8` 的 570 字节等于 95×6，与常见的 95 个可打印 ASCII 字符点阵布局相符。中文或扩展字库还可能包含索引信息，不能只靠字节数推定字符数量。

**最后 16 个字节，是将来放进 RAM 的变量初值。**

文件末尾的实际内容如下：

```text
偏移 0x3FF8：01 00 00 00
偏移 0x3FFC：10 00 00 00
偏移 0x4000：00 00 00 00
偏移 0x4004：00 12 7A 00
```

结合 MAP，可以对应到这些运行时变量：

| Flash 中的初值位置 | 运行时 RAM 地址 | 对象 | 初始内容 |
|---|---|---|---|
| `0x08003FF8` | `0x20000000` | `uwTickFreq` 及随后填充 | 变量为 1；变量本体占 1 字节 |
| `0x08003FFC` | `0x20000004` | `uwTickPrio` | 16 |
| `0x08004000` | `0x20000008` | `uwTick` | 0 |
| `0x08004004` | `0x2000000C` | `SystemCoreClock` | 8,000,000 |

例如 `00 12 7A 00` 按小端序是 `0x007A1200`，十进制为 8,000,000。这里表示 `SystemCoreClock` 的初始值，不能据此认定程序运行后的系统时钟始终是 8 MHz。

为什么 RAM 变量的初值会出现在 Flash 镜像里？因为 RAM 中的运行数据需要在启动时建立。初值保存在非易失性存储器中，启动代码再把它们复制到指定的 RAM 地址。

本文件的 `0x3FD8`～`0x3FF7` 还保存了 32 字节的运行库初始化区域表。结合 MAP 和字节内容，这张表描述了把 16 字节初值送到 `0x20000000`，以及为从 `0x20000010` 开始的 `0xDA0` 字节区域执行清零初始化所需的信息。

**运行时需要的 RAM，不会全部原样放进 BIN。**

本工程的 `OLED_DisplayBuf` 占 1,024 字节，位于 `0x20000010`，属于零初始化区域。它需要在 RAM 中存在，但 BIN 不必专门保存 1,024 个零来表达它；运行库按初始化信息清零即可。

本次链接统计如下：

| 项目 | 大小 | 含义 |
|---|---:|---|
| Code | 12,792 字节 | 链接器归入代码的区域，其中也可能夹有局部数据 |
| RO Data | 3,584 字节 | 只读数据，如向量表、字库及初始化表 |
| RW Data | 16 字节 | 带有镜像初值的可写数据 |
| ZI Data | 3,488 字节 | 零初始化或预留 RAM 区域，本工程包含堆栈预留 |

所以 BIN 大小为：

```text
12,792 + 3,584 + 16 = 16,392 字节
```

而本次链接分配的 RAM 区域为：

```text
16 + 3,488 = 3,504 字节
```

两者统计的是不同资源。3,504 字节是链接时分配的 RAM 区域规模，不能作为运行时栈、堆一定够用的证明。

**把整个文件连起来看，就能理解它如何变成运行中的程序。**

这个文件的主要布局可以概括为：

| 文件偏移范围，含两端 | 内容 | 大小 |
|---|---|---:|
| `0x0000`～`0x00EB` | 初始栈顶和异常、中断向量表 | 236 字节 |
| `0x00EC`～`0x32E3` | 启动代码、库函数、用户代码及夹杂的数据、填充 | 12,792 字节 |
| `0x32E4`～`0x3FAD` | 三组 OLED 字库数据 | 3,274 字节 |
| `0x3FAE`～`0x3FD7` | 时钟相关查找表 | 42 字节 |
| `0x3FD8`～`0x3FF7` | 运行库初始化区域表 | 32 字节 |
| `0x3FF8`～`0x4007` | RAM 变量的初始内容 | 16 字节 |

在正确配置为从该 Flash 镜像启动的条件下，处理器取得初始栈指针和复位入口，执行启动代码；运行库建立 RAM 中的初始数据，然后进入 `main`。之后，程序按逻辑读取常量、调用驱动函数，并在中断发生时通过向量表转入相应处理程序。

BIN 因而同时装着“要执行的指令”和“指令要使用的数据”。它通常不保留源代码注释、完整类型信息和函数符号，不能直接恢复成原来的 C 工程；配合同次构建的 AXF、MAP、HEX 与源码，才能把某段字节可靠地对应到一个函数、一组字库或一个变量。

本文所分析文件的 SHA-256 为：

```text
F8AF28E320001EC198F2D658B8BA34616282B49AA0301567FC851D91A99932DE
```

以后重新编译时，即使文件仍叫 `myBalanceCar.bin`，地址和内容也可能改变。上面的具体偏移、大小和入口值只对应这一份镜像。
