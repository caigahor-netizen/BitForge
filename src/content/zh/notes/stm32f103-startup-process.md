把程序烧进单片机，接上电源，屏幕就亮了。这个过程背后，至少有三个不同的问题：电路怎样获得工作的条件？处理器怎样知道第一段程序在哪里？C 语言里的全局变量、函数和中断，又是怎样变成实际运行状态的？

**单片机能运行起来，是芯片的复位机制、存储器映射、编译链接结果、启动代码和应用初始化共同配合的结果。** `main()` 只是这条链路中的一个节点。在执行到它之前，硬件已经选过启动来源，CPU 已经取过指令，运行库也已经处理过 RAM。

本文以 STM32F103C8T6 为对象，用一份真实固件把全过程串起来。阅读时可以始终抓住三件事：**当前 CPU 正从哪里取指令，当前数据存在哪里，当前是谁决定下一步动作。**

本文依据 2026 年 10 月 10 日提供的“相关文件”目录：`startup_stm32f103xb.s`、`myBalanceCar.bin`、`myBalanceCar.hex` 和 `myBalanceCar.map`。同时核对了本地数据手册、参考手册，以及原工程中可以生成完全相同 BIN 的 AXF 反汇编。文章中的具体地址属于这一份固件，不是 STM32F103 所有程序都固定使用的地址。

这次 BIN 为 **23,180 字节**，与[上一篇 BIN 解析文章](/zh/notes/stm32-bin-firmware/)分析的 16,392 字节版本不同，不能混用两篇中的函数地址和 RAM 布局。本文只进行了文件分析和手册核对，没有实际给开发板上电测量。

**一、先把完整启动链放在一起看。**

正常从用户 Flash 启动时，可以把主要过程理解为：

```text
电脑上的开发阶段
C 源码、汇编启动文件、库
    → 编译 / 汇编
    → 链接并确定地址
    → AXF / ELF、MAP
    → 导出 HEX / BIN
    → 下载工具把内容写入芯片 Flash

芯片每次复位后的运行阶段
电源与复位条件满足，内部启动时钟可用
    → 芯片采样 BOOT 引脚，选择启动来源
    → 在启动映射下读取初始栈指针和复位向量
    → 执行 Reset_Handler
    → 调用 SystemInit
    → 进入 C 运行库 __main
    → 复制 .data 初值、清零 ZI 区域
    → 进入用户 main
    → HAL、时钟和外设初始化
    → 主循环运行，中断按事件插入执行
```

上半部分通常在开发和升级时发生，下半部分每次复位都会发生。正常独立运行时，不需要电脑在旁边持续发送指令，也不需要 Keil 一直打开。

这是一张逻辑顺序图，并不表示电源监督、内部振荡器和各复位电路在晶体管级严格串行工作。准确的电气时序应以芯片手册为准；我们关心的是 CPU 开始执行软件前后，各部分分别承担什么职责。

**二、先认识这颗芯片：处理器、存储器和外设各做什么。**

STM32F103C8T6 是一颗包含 Cortex-M3 内核的微控制器。CPU 内核负责取指、运算、分支和异常处理；Flash 保存固件；SRAM 保存运行中的可变数据；GPIO、定时器、串口、ADC 等外设负责与外部世界交互。

对本文最重要的规格是：

| 项目       | STM32F103C8T6 的含义或规格                              |
| -------- | ------------------------------------------------- |
| 内核       | Arm Cortex-M3，32 位，执行 Thumb / Thumb-2 指令          |
| 最高系统频率   | 72 MHz；这是允许配置到的上限，不是复位后自动采用的频率                    |
| 用户 Flash | 标称 64 KiB，即 65,536 字节                             |
| SRAM     | 20 KiB，即 20,480 字节                                |
| 封装       | `C` 表示 48 引脚，`T` 表示 LQFP；C8T6 为 LQFP48            |
| 容量代码     | `8` 表示 64 KiB Flash；不要把同一手册中的 xB 型号 128 KiB 套到 C8 |
| 温度等级     | `6` 对应 −40～85 ℃ 的型号等级                             |
| 应用供电     | VDD 的规定工作范围为 2.0～3.6 V；开发板常用 3.3 V                |

这些规格来自本地《STM32F103x8B 数据手册》器件特性、器件对比表及订货编码。官方同系列资料可从 [STM32F103C8 产品页](https://www.st.com/en/microcontrollers-microprocessors/stm32f103c8)获取。本文按官方标称容量说明，不依赖个别芯片可能存在的非保证容量。

“32 位单片机”并不表示每条机器指令恰好都是 4 字节，也不表示只能操作 32 位数据。它可以读写字节、半字和字，Thumb 指令也有 16 位和 32 位编码。

**三、没有可靠的供电、复位和时钟，软件就没有开始执行的条件。**

从电路角度，启动的第一步是给芯片正确供电。LQFP48 封装中，与最小系统密切相关的引脚如下。本表已对照本地数据手册第 26 页的封装引脚图。

| 引脚功能                             | LQFP48 引脚号 | 与启动的关系                     |
| -------------------------------- | ---------- | -------------------------- |
| VDD                              | 24、36、48   | 数字电源，所有电源脚都要正确连接           |
| VSS                              | 23、35、47   | 数字地，所有地脚都要正确连接             |
| VDDA、VSSA                        | 9、8        | 模拟电源和地，也关系到片内模拟、RC、PLL 等电路 |
| VBAT                             | 1          | 备份域供电；不使用独立电池时按手册接到 VDD    |
| NRST                             | 7          | 低有效复位引脚                    |
| BOOT0                            | 44         | 选择启动模式                     |
| PB2 / BOOT1                      | 20         | 与 BOOT0 共同决定启动来源           |
| PD0 / OSC_IN、PD1 / OSC_OUT       | 5、6        | 外部高速晶振 HSE 引脚              |
| PC14 / OSC32_IN、PC15 / OSC32_OUT | 3、4        | 外部低速晶振 LSE，常用于 RTC         |
| PA13 / SWDIO、PA14 / SWCLK        | 34、37      | SWD 下载与调试接口                |

VDDA 不能因为“不使用 ADC”就不接。按此器件手册，VDDA、VSSA 应与对应的电源和地正确连接；ADC 使用时另有更严格的供电条件。VBAT 只维持备份域，不能靠它单独给整个 CPU 供电。

供电线上还需要去耦。快速变化的内部电流不能完全依赖远处电源经过较长导线及时提供，因此电源脚附近通常放置小容量陶瓷电容，并搭配较大的储能电容。应按实际封装布置，例如各 VDD 旁的 100 nF 去耦；VDDA 的滤波、去耦参考手册电源图。数据手册第 36 页是系列通用图，画了多个封装的供电连接，不能把图中电源脚数量机械照搬到 48 脚封装。

芯片内部有 POR/PDR，也就是上电、掉电复位监督电路。电源未达到要求时，芯片保持复位；条件满足后，才释放处理器进入启动过程。这里不能把“电压刚到 2.0 V”理解成所有板子上完全相同的精确释放时刻，阈值范围和复位延时要看电气参数表。

NRST 被外部拉低也会触发复位。看门狗、软件请求等同样可以产生复位。**复位和断电不是同一件事**：复位让相关控制状态重新开始，Flash 中的程序通常仍然存在，SRAM 也不等于已经被硬件全部清零。不同复位源对备份域等状态的影响还有区别。

PVD 是另一个概念：它是软件可使能的可编程电压检测功能，可产生相关事件或中断。不能把 PVD 与始终承担上电、掉电监督的 POR/PDR 混为一谈。

以上硬件说明依据本地数据手册第 15～16、26、36、38～40 页，以及本地 RM0008 第 7.1 节。没有这些条件，Flash 即使写得完全正确，CPU 也可能无法稳定执行。

**四、CPU 需要时钟，但不必等外部晶振起来才能执行第一条指令。**

STM32F103 在系统复位后，默认使用内部 **HSI 8 MHz RC 振荡器**作为系统时钟来源。外部 HSE 晶振和 PLL 并不是 CPU 执行复位处理函数的前提。

因此，一个按 HSI 设计的最小程序可以不使用外部高速晶振。反过来，如果应用明确要求启动 HSE，外部晶振电路没有焊好，程序可能已经走到时钟初始化，随后等待就绪、超时，或者进入错误处理。

这就是“芯片完全没启动”和“芯片启动了，但初始化失败”的区别。肉眼看 LED 不亮，无法直接区分两者。

时钟是电路状态更新的节拍。它没有告诉 CPU“执行哪一个 C 函数”；指令的位置由 PC 和分支结果决定。系统时钟提高到 72 MHz，也不等于每秒恰好执行 7,200 万条 C 语句，指令周期、访存等待和流水线都会影响实际执行速度。默认 HSI 的选择见本地 RM0008 第 7.2.6 节。

**五、先建立内存地图，才能看懂后面的地址。**

Cortex-M3 使用统一的地址空间。CPU 读写一个地址时，由地址译码和总线决定访问 Flash、SRAM 还是外设寄存器。地址空间很大，不代表芯片真的装了同样大的存储器。

| 地址或范围 | 在这颗芯片中的用途 | 断电后通常怎样 |
|---|---|---|
| `0x00000000` 附近 | 复位取向量所用的启动空间；其映射与 BOOT 选择有关 | 是地址映射问题，不是一块额外的大 Flash |
| `0x08000000`～`0x0800FFFF` | C8 标称 64 KiB 用户 Flash | 程序和已写入数据保留 |
| `0x1FFFF000`～`0x1FFFF7FF` | 中容量 F1 的 2 KiB System memory 信息区，包含 ST 出厂启动程序 | 不随普通 RAM 掉电丢失 |
| `0x1FFFF800`～`0x1FFFF80F` | 选项字节区域，如保护和部分启动相关配置 | 非易失 |
| `0x20000000`～`0x20004FFF` | 20 KiB SRAM | 不能依赖掉电后保留 |
| `0x40000000` 一带 | 外设寄存器地址空间，不是普通 RAM | 依外设和复位类型变化 |
| `0xE000E000` 一带 | Cortex-M 内核私有外设，如 SysTick、NVIC、SCB | 由内核复位和软件控制 |

Flash 信息区还含器件标识等信息，不能把相关区域的每个字节都看成可执行 Bootloader 代码。System memory 也不是用户程序在 `0x08000000` 的那块 Flash 的别称。

这张地图依据本地 RM0008 第 3 章及中容量器件 Flash 组织表。F1 不同容量、互联型器件的系统存储器地址和功能可能不同，不能跨型号照抄。

三个常见地址可以帮助建立直觉：

```text
0x08004B90：本固件 main 的指令在 Flash 中的位置
0x2000000C：SystemCoreClock 变量在 RAM 中的位置
0x40021018：RCC_APB2ENR 外设时钟使能寄存器的位置
```

同样是“一个地址”，访问第一种通常是在取代码，访问第二种通常是在读写数据，访问第三种可能改变硬件状态。CPU 不认识变量名 `SystemCoreClock`，它执行的是针对相应地址的机器指令。

**六、BOOT0、BOOT1 决定最初从哪一类存储器启动。**

STM32F103C8T6 的启动模式表如下，注意本表把 BOOT0 放在第一列：

| BOOT0 | BOOT1 / PB2 | 启动来源 | 典型用途 |
|---:|---:|---|---|
| 0 | 任意 | 用户主 Flash | 运行已经烧录的用户程序 |
| 1 | 0 | System memory | 运行 ST 出厂 Bootloader，进行串口下载等 |
| 1 | 1 | SRAM | 特定的 RAM 调试、装载和运行场景 |

本地 RM0008 第 3.4 节说明：BOOT 引脚值在复位后的 SYSCLK 第 4 个上升沿锁存。实际电路应让它们在复位前后保持稳定，不能把它当作给软件留出的“临时拨一下”窗口。运行中改变 BOOT0，并不会让正在执行的程序立即切换到另一个存储器。

正常从 Flash 启动时，芯片把主 Flash 映射到 `0x00000000` 的启动空间，同时保留其原始地址 `0x08000000`：

```text
复位时访问 0x00000000 → 看到 Flash 0x08000000 的内容
复位时访问 0x00000004 → 看到 Flash 0x08000004 的内容
```

这是**地址别名或映射**，不是把 64 KiB Flash 复制了一份，更不是把固件搬到 RAM。

从 System memory 启动也有对应的启动映射。SRAM 启动则需要特别小心：RM0008 明确说 SRAM 仍只在 `0x20000000` 地址范围可访问，芯片通过特殊机制支持从 SRAM 启动，初始化代码需要把向量表定位到 SRAM。不要把“Flash 有零地址别名”简单推广成“SRAM 也有完全相同的普通别名”。

SRAM 断电后没有可靠固件内容，因此把 BOOT0、BOOT1 都拨高，不会凭空在 RAM 里生成一个程序。通常要先由调试器或其他装载程序准备 RAM 内容，并按 RAM 执行地址链接。

**七、在上电之前，代码已经怎样变成了这些字节？**

源代码中的 `main`、`SystemInit`、`OLED_Init` 是人使用的符号。编译器把 C 代码翻译成目标机器代码，汇编器处理启动文件，链接器再把所有目标文件和库组合起来。

链接器的关键工作包括：安排代码和数据位置，解析函数与变量引用，为指令补上最终地址或相对跳转距离，并删除不需要保留的部分。

| 文件 | 它保存什么 | 在启动分析中有什么用 |
|---|---|---|
| `.c`、`.h` | 源代码、声明、类型、宏 | 理解程序意图 |
| `.s` | 启动汇编源文件 | 理解向量表定义、复位入口和启动接口 |
| `.o` | 编译或汇编后的目标文件 | 尚需链接的代码、数据、符号和重定位信息 |
| `.axf` / `.elf` | 链接后的可执行映像，可能带调试信息 | 确定符号、入口、装载区域并反汇编 |
| `.map` | 链接器生成的布局与引用报告 | 查函数地址、变量地址、内存占用、被删除的段 |
| `.hex` | 有地址和校验信息的文本记录 | 告诉下载工具各段字节应写到哪里 |
| `.bin` | 平坦的原始字节镜像 | 作为烧录或升级载荷，装载地址需另外给出 |

对这份工程，MAP 标明使用 **ARM Compiler 5.06 update 7**，并链接了 `mc_w.l` 等 MicroLIB 组件。后文中的 `__main`、`__scatterload` 是这一套工具链的实际实现。GCC 工程可能直接在 `Reset_Handler` 中搬运 `.data`、清零 `.bss`，再调用 `__libc_init_array` 和 `main`；目的相近，但函数名、顺序和汇编形式不必相同。

`startup_stm32f103xb.s` 文件名中的 `xB` 不等于这份程序一定针对 128 KiB 芯片。此类启动文件服务于相关中容量 F103 型号，共享一套适用的向量布局；最终 Flash、RAM 容量还要看具体器件和链接配置。

**八、拿这份 HEX 手算一次，就能知道 Flash 最开始装的是什么。**

Intel HEX 是文本格式，基本结构是：

```text
:LL AAAA TT [DATA...] CC

LL    本记录数据字节数
AAAA  地址字段
TT    记录类型
DATA  数据
CC    校验和
```

`00` 是数据记录，`04` 设置后续数据地址的高 16 位，`05` 是起始线性地址记录，`01` 是文件结束记录。每一行除冒号外的字节值相加，连同校验和，低 8 位应为零。格式和 MDK 对入口记录的解释见 [Keil Intel HEX 文档](https://www.keil.com/support/docs/1584/_hlp_hexfile.htm)。

你的文件第一行是：

```text
:020000040800F2
```

按字段拆开为：

```text
: 02 0000 04 0800 F2
```

它设置的地址基值为 `0x0800 << 16 = 0x08000000`。这行中的 `08 00` 是地址记录字段，不是要把这两个字节写进程序头部。

第二行是：

```text
:10000000580D0020050100082D3500089F2D00081F
```

它告诉下载工具：向基址加偏移 `0x0000` 的位置写入 16 字节。数据区拆成四组，就是：

```text
Flash 地址     实际写入的四个字节    按小端解释的 32 位值
0x08000000     58 0D 00 20           0x20000D58
0x08000004     05 01 00 08           0x08000105
0x08000008     2D 35 00 08           0x0800352D
0x0800000C     9F 2D 00 08           0x08002D9F
```

本行校验和之前的字节相加为 `0x1E1`，低 8 位为 `0xE1`；再加上 `0x1F` 得到 `0x200`，低 8 位为零。

注意两种“顺序”同时存在：HEX 地址字段按格式阅读，而它承载的 ARM 内存数据要按目标的小端序解释。`58 0D 00 20` 并不是地址 `0x580D0020`。

这份 HEX 共 1,452 条记录，其中 1,449 条数据记录、1 条扩展线性地址记录、1 条入口记录、1 条结束记录。所有行校验和通过，数据连续覆盖：

```text
0x08000000 ～ 0x08005A8B
```

抽出的有效数据与 BIN 的 23,180 个字节完全相同。HEX 文件本身有 65,248 字节，是因为每个数据字节被写成两个十六进制文本字符，还有地址、校验和、换行等开销。**不能拿 HEX 文件在电脑上的大小直接当成 Flash 占用。**

这也解释了为什么下载器要区分文件格式。如果把 HEX 文本当作裸 BIN 写入，Flash 开头可能是冒号、数字对应的 ASCII 编码，初始栈指针和复位向量就全错了。CPU 不会在上电后自己解析 Intel HEX 文本。

**九、硬件复位后先读取两个数：栈顶和复位入口。**

当正常选择用户 Flash 启动时，Cortex-M3 从启动空间取初始主栈指针 MSP，再取复位向量。对当前镜像，对应关系是：

| 读取位置 | 通过 Flash 映射得到的内容 | 硬件用途 |
|---|---|---|
| `0x00000000` | `0x20000D58` | 建立初始 MSP |
| `0x00000004` | `0x08000105` | 指定复位处理程序与 Thumb 状态 |

硬件执行的不是“从地址 0 开始，把第一个字当成指令”，而是“先把表头解释为初始状态和入口”。因此，BIN 开头的 `58 0D 00 20` 是数据，不是用户程序第一条指令。

那么，读取这两个数的动作又是谁编程实现的？它是处理器复位控制逻辑规定的硬件行为，不需要先运行你的 C 代码。芯片设计已经约定了复位时应发起哪些访问、怎样建立初始处理器状态，因此不会陷入“要执行程序才能找到第一条程序”的循环。硬件只认这些数值与规则，并不知道源文件中有一个函数叫 `Reset_Handler`。

复位入口值 `0x08000105` 的最低位为 1，表示 Thumb 状态。实际第一条指令位于：

```text
0x08000105 & ~1 = 0x08000104
```

这不是从奇数地址读取一个半字。Cortex-M3 的有效处理程序入口需要正确的 Thumb 标记。向量表结构和内核寄存器行为见 [ST PM0056](https://www.st.com/resource/en/programming_manual/cd00228163.pdf)。

初始栈顶 `0x20000D58` 位于 SRAM 中，但它不等于 SRAM 的物理末尾。C8T6 的 SRAM 最高有效字节地址是 `0x20004FFF`，其上边界是 `0x20005000`；本工程只把栈安排在 RAM 前部的一段区域。

复位后处理器在特权 Thread 模式下使用 MSP。Reset 不是一次普通函数调用，没有一个上层 C 调用者把它调用进来，也没有可依赖的普通返回现场。

**十、启动文件中的指令和伪指令，哪些真的在 CPU 上运行？**

这份 `.s` 文件中的向量表开始于：

```asm
AREA    RESET, DATA, READONLY
EXPORT  __Vectors

__Vectors
    DCD __initial_sp
    DCD Reset_Handler
    DCD NMI_Handler
    DCD HardFault_Handler
```

`AREA` 告诉汇编器创建或选择一个段；`DCD` 生成 32 位数据；`EXPORT` 声明符号可被其他目标文件引用。这些都是构建阶段的指令，不是 CPU 上电后执行的操作码。

链接器知道 `__initial_sp` 和各函数最终落在哪里，把相应值写进表中。结果就是我们在 BIN 开头看到的 `0x20000D58`、`0x08000105` 等数值。

本文件的向量表大小是 `0xEC = 236` 字节，共 59 个表项：16 个核心表项位置，加 43 个外设 IRQ 表项。第一个位置是初始栈指针，不能把 59 项全部叫作“59 个外设中断”。

真正的复位处理代码是：

```asm
Reset_Handler PROC
    EXPORT Reset_Handler [WEAK]
    IMPORT __main
    IMPORT SystemInit

    LDR R0, =SystemInit
    BLX R0
    LDR R0, =__main
    BX  R0
    ENDP
```

它表达的逻辑是：取 `SystemInit` 的入口，带返回地址调用它；函数返回后，取 `__main` 的入口并跳过去。

实际反汇编与机器字节如下：

| 实际指令地址 | BIN 中字节 | 反汇编含义 |
|---|---|---|
| `0x08000104` | `06 48` | 从常量池读取 `SystemInit` 入口到 R0 |
| `0x08000106` | `80 47` | `BLX R0`，调用 `SystemInit` |
| `0x08000108` | `06 48` | 从常量池读取 `__main` 入口到 R0 |
| `0x0800010A` | `00 47` | `BX R0`，转交运行库 |

两个常量池位置为：

```text
0x08000120 存放 0x08003B95：SystemInit 的带 Thumb 标记入口
0x08000124 存放 0x080000ED：__main 的带 Thumb 标记入口
```

因此，`LDR R0, =SystemInit` 并不是先执行 `SystemInit`；它先取得地址，接下来的分支指令才改变控制流。这里的 `BLX` 会建立返回所需的 LR，`BX` 则只是转移到指定入口。

启动文件中的 `[WEAK]` 表示弱定义。如果用户 C 文件提供了同名的有效强定义，链接器可选择强定义。这就是为什么你可以在 `stm32f1xx_it.c` 里实现 `SysTick_Handler`，而不用直接修改启动文件中的默认处理函数。

许多未实现的 IRQ 最终共用 `B .` 死循环。本镜像不少外设向量指向 `0x0800011F`，实际指令地址为 `0x0800011E`。如果程序停在那里，应检查是不是使能了某个中断，却没有提供正确的处理函数。

**十一、名字叫 SystemInit，不代表它一定设置了 72 MHz。**

这个问题在当前固件里尤其清楚。`SystemInit` 的最终反汇编只有：

```asm
0x08003B94:  4770    BX LR
```

也就是直接返回，机器字节是 `70 47`。

原工程的 `system_stm32f1xx.c` 中，相关动作受芯片型号、外部 RAM、`USER_VECT_TAB_ADDRESS` 等条件编译控制。本次构建并没有留下实际的初始化动作。

所以不能根据启动文件顶部“配置时钟”一类概述注释，就断定当前二进制一定在此处配置了 PLL。**对这一份固件，`SystemInit` 返回时仍依靠复位默认环境，真正的应用时钟配置在 `main()` 里。**

CMSIS 定义了 `SystemInit` 和 `SystemCoreClock` 等接口的用途，但具体芯片包和工程怎样实现，仍要看实际代码。[CMSIS 系统与时钟接口说明](https://arm-software.github.io/CMSIS_5/Core/html/group__system__init__gr.html)

还有一个顺序限制：在此工程中，`SystemInit` 位于 RAM 的 C 运行环境初始化之前。如果你在这里新增代码，不应随意依赖尚未初始化的全局变量、静态对象或依赖这些对象的库函数。堆栈已经有初始位置，并不代表完整 C 运行环境已经建立。

**十二、__main 和 main 是两回事；HEX 的“入口”也不等于复位入口。**

本 HEX 倒数第二行是：

```text
:04000005080000ED02
```

它是 `05` 类型记录，载荷为 `0x080000ED`。MAP 同样写着：

```text
Image Entry point : 0x080000ed
```

然而，Flash 第二个字明明是 `0x08000105`。这是矛盾吗？不是，它们描述的是不同入口：

| 名称 | 本次符号入口值 | 谁使用它 |
|---|---|---|
| 复位向量 | `0x08000105` | 芯片复位启动机制，用来进入 `Reset_Handler` |
| 链接映像 / HEX 标注入口 | `0x080000ED` | 构建、转换和部分装载工具的映像入口信息；本例是 `__main` |
| 用户主函数 | `0x08004B91` | C 运行环境准备好后转入的 `main` |

MDK 的 `05` 记录可以标注运行库的 pre-main 入口。它不替代 Flash 里的复位向量，也不构成一段要烧入地址零的普通数据。独立上电的芯片不会打开 HEX 文件寻找这一行。[Keil 对 Start Linear Address 的说明](https://www.keil.com/support/docs/1584/_hlp_hexfile.htm)

本次 `__main` 的实际指令起点是 `0x080000EC`。反汇编显示它会重新把 SP 设为 `0x20000D58`，调用 `__scatterload`，随后转到 `main`。启动初期的硬件已经先建立过 MSP，因此 `Reset_Handler` 调用 `SystemInit` 时并不是没有栈。

```text
Reset_Handler @ 0x08000104
    │
    ├─ BLX → SystemInit @ 0x08003B94 → 返回
    │
    └─ BX  → __main @ 0x080000EC
                 │
                 ├─ 建立运行库所需的初始 SP
                 ├─ __scatterload @ 0x08000684
                 │     ├─ 复制初始化数据
                 │     └─ 清零指定 RAM 区域
                 └─ 转到 main @ 0x08004B90
```

各段代码在 Flash 中的排列顺序，与它们实际执行的先后顺序不必一致。CPU 不是从文件头一路线性“读完 BIN”，而是由入口、条件分支、调用、返回和异常不断决定下一处执行地址。

**十三、RAM 为什么要初始化：全局变量的初值最初在 Flash 里。**

考虑下面的示意代码，它用于解释机制，不是声称当前工程里恰好存在这些变量：

```c
uint32_t speed_limit = 100;   // 通常需要保存可写变量的初值
uint32_t tick_count;          // 静态存储期对象，需要零初始化
static uint8_t rx_buf[256];   // 同样需要零初始化
const uint8_t font[] = { 0x00, 0x7E, 0x42 }; // 通常作为只读常量
```

运行时要能修改 `speed_limit`，因此通常把它放到 RAM。但断电后 RAM 没有可靠内容，数值 100 需要保存在 Flash 镜像里，启动时再复制到它的 RAM 位置。

`tick_count` 和 `rx_buf` 的初始内容都是零，镜像通常不必保存一大串零，而是让启动代码按范围清零。常量字库则通常保留在 Flash 中，直接被读取。

这分别对应常说的 `.data`、`.bss` / ZI 和只读数据区域。具体归类由编译器、优化和链接配置决定：即使一个变量初值为零，也不保证最终一定归入 `.bss`；本次 `uwTick` 就在有装载初值的区域中。

普通未初始化的自动局部变量也不能套用这一规则。它并不因为“上电时清过 RAM”就获得 C 语言保证的零值；它可能复用栈内容，也可能只存在于寄存器中。

本镜像最后 24 字节位于 `0x08005A74`～`0x08005A8B`，启动时复制到 RAM `0x20000000`～`0x20000017`：

| Flash 装载地址 | RAM 执行地址 | 对象 / 内容 | 镜像中的初始值 |
|---|---|---|---|
| `0x08005A74` | `0x20000000` | `uwTick` | 0 |
| `0x08005A78` | `0x20000004` | `uwTickPrio` | 16 |
| `0x08005A7C` | `0x20000008` | `uwTickFreq`，后接 3 字节填充 | 变量为 1，变量本体占 1 字节 |
| `0x08005A80` | `0x2000000C` | `SystemCoreClock` | 8,000,000 |
| `0x08005A84` | `0x20000010` | `bootloader.o` 的 2 字节可写数据及填充 | 零 |
| `0x08005A88` | `0x20000014` | `__stdout` | 零 |

注意，“Load address”表示初值在装载镜像中的位置；“Exec address”表示程序运行时使用的位置。对于这里的可写变量，两者分别在 Flash 和 RAM。对于直接在 Flash 中执行的代码，两者通常相同。

这是一份变量初值在两个地方各有作用的情况，不是整个程序必须先复制到 RAM 才能运行。

**十四、直接解码运行库初始化表：这 32 个字节在指挥什么？**

MAP 中有：

```text
Region$$Table$$Base  = 0x08005A54
Region$$Table$$Limit = 0x08005A74
```

这 32 字节包含两项，每项 16 字节。根据这份二进制的运行库反汇编，每项依次提供源地址、目的地址、长度、处理函数地址。

| 项目 | 源地址字段 | 目的地址 | 长度 | 处理函数实际地址 |
|---|---|---|---|---|
| 复制 | `0x08005A74` | `0x20000000` | `0x18`，24 字节 | `0x0800425C`，`__scatterload_copy` |
| 清零 | `0x08005A8C` | `0x20000018` | `0xD40`，3,392 字节 | `0x0800426C`，`__scatterload_zeroinit` |

用伪代码表达本次效果，就是：

```c
// 表达最终效果，不是运行库源码的逐字还原。
copy_bytes(0x20000000, 0x08005A74, 24);
zero_bytes(0x20000018, 3392);
```

清零项里的“源地址”恰好是镜像结束的后一地址。它不是说还需要从 BIN 后面读出 3,392 个字节；清零处理函数本来就不需要读取源数据。反汇编显示它不断向目的 RAM 写零。

这个表里处理函数地址的最低位是 0，而前面讲向量入口最低位应为 1，也不矛盾：**这张表不是硬件异常向量表。** 当前 `__scatterload` 在调用处理函数前，显式把地址与 1 做或运算，再执行 `BLX`。表的格式由运行库定义，向量表的格式由内核定义。

所以真正可靠的分析不是“见到一个地址就套同一条规则”，而是看谁读取这个数据，以及读取后怎样使用。

**十五、把本固件的 Flash 与 RAM 画出来，栈和堆就不再抽象了。**

本次 Flash 布局是：

```text
0x08000000 ┌────────────────────────────────────┐
           │ 向量表：0xEC 字节                  │
0x080000EC ├────────────────────────────────────┤
           │ 代码、常量池、部分字符串与填充      │
           │ Reset_Handler / 库函数 / main 等   │
0x08004CC0 ├────────────────────────────────────┤
           │ OLED 字库、图标、时钟相关查找表     │
0x08005A54 ├────────────────────────────────────┤
           │ 运行库初始化表：32 字节            │
0x08005A74 ├────────────────────────────────────┤
           │ RAM 初值的 Flash 副本：24 字节      │
0x08005A8C ├────────────────────────────────────┤ ← 本 BIN 结束的后一地址
           │ 本次镜像未覆盖的应用 Flash 空间    │
0x0800F800 ├────────────────────────────────────┤
           │ 参数页 A：1 KiB                    │
0x0800FC00 ├────────────────────────────────────┤
           │ 参数页 B：1 KiB                    │
0x08010000 └────────────────────────────────────┘ ← 64 KiB Flash 上边界
```

MAP 的应用装载区域上限为 `0xF800`，也就是 62 KiB；原工程参数地址常量和相应反汇编对应最后两个 1 KiB 页。它们用于应用参数保存，不包含在本次 23,180 字节 BIN 的有效载荷里。

因此，BIN 不是整个 64 KiB Flash 的完整读回快照，也不包含芯片运行后写入参数页的最新数据。文件没覆盖的地址，真实芯片里可能是已擦除的 `0xFF`，也可能保留旧内容，取决于烧录器的擦除策略和历史状态。

RAM 则是：

| RAM 范围，含两端 | 大小 | 本次用途 |
|---|---:|---|
| `0x20000000`～`0x20000017` | 24 字节 | 带镜像初值的可写数据及填充 |
| `0x20000018`～`0x20000417` | 1,024 字节 | `OLED_DisplayBuf` |
| `0x20000418`～`0x200004BF` | 168 字节 | I²C 相关对象 |
| `0x200004C0`～`0x20000597` | 216 字节 | 定时器相关对象 |
| `0x20000598`～`0x20000737` | 416 字节 | UART 与 DMA 相关对象 |
| `0x20000738`～`0x20000757` | 32 字节 | Flash 驱动状态 |
| `0x20000758`～`0x20000957` | 512 字节 | 两个 Bootloader 命名的通信缓冲区 |
| `0x20000958`～`0x20000D57` | 1,024 字节 | 栈预留区 |
| `0x20000D58`～`0x20004FFF` | 17,064 字节 | 此 MAP 未分配的其余 SRAM |

栈的初始 SP 为 `0x20000D58`，指向栈区上边界。典型压栈会先把 SP 向较低地址移动，再保存寄存器；函数返回时恢复。例如在初始 SP 下压入一个 32 位值后，新的 SP 可成为 `0x20000D54`。

栈会用于保存函数现场、部分局部变量和中断现场。它不是一块永久只用于某一个函数的空间；调用结束后，相应位置会被后续调用复用。编译器也可能把局部变量留在寄存器，而根本不放进栈。

特别要看清这份启动文件中的两行：

```asm
Stack_Size EQU 0x400
Heap_Size  EQU 0x200
```

`EQU` 定义构建阶段的常量。`SPACE` 配合段属性表达预留空间，`ALIGN=3` 表示按 2³，即 8 字节对齐；这些都不是上电时调用一次内存分配器。

虽然源文件定义了 512 字节堆，本次 MAP 明确写着：

```text
Removing startup_stm32f103xb.o(HEAP), (512 bytes).
```

最终 RAM 表中没有独立的 512 字节 HEAP 段。因此，不能只看 `.s` 就把这 512 字节计入已分配 RAM，也不能据此认定 `malloc` 已具备某种固定容量。是否需要堆以及怎样提供堆，要结合运行库、保留规则与最终链接结果。

同理，启动文件中的 `NOINIT` 不能单独证明某块 RAM 一定不会被启动代码触碰。这份实际运行库的清零表覆盖到 `0x20000D57`，包含了栈预留区。若要保留复位前的特定 RAM 数据，需要专门设计链接中的不初始化区域，并确保启动代码确实跳过它。

MAP 的最终统计为：

```text
Code    = 19,412 字节
RO Data =  3,744 字节
RW Data =     24 字节
ZI Data =  3,392 字节

Flash 镜像 = Code + RO Data + RW Data = 23,180 字节
RAM 区域   = RW Data + ZI Data        =  3,416 字节
```

3,416 字节已经包含本次预留的 1,024 字节栈。RAM 后面还有很多未分配空间，也不意味着当前栈能无限扩张：这个栈向低地址增长，越过 `0x20000958` 后会碰到下面的数据区。需要更大栈时，应修改配置并重新链接，而不是看见物理 RAM 有余量就认为不会溢出。

**十六、进入 main 以后，应用才把芯片配置成需要的样子。**

反汇编表明，本固件 `main` 位于 `0x08004B90`，开头先为自己的局部栈空间减去 `0x18`，然后依次调用：

```c
// 由本次 main 的反汇编整理出的调用顺序。
HAL_Init();
SystemClock_Config();
MX_GPIO_Init();
MX_DMA_Init();
MX_USART1_UART_Init();
MX_USART2_UART_Init();
MX_I2C2_Init();
MX_TIM1_Init();
MX_TIM2_Init();
MX_TIM3_Init();
MX_I2C1_Init();
HAL_Delay(100);
OLED_Init();
// 随后读取、保存参数，并更新 OLED 显示。
bootloader_init();

for (;;) {
    bootloader_process();
    HAL_Delay(1000);
}
```

这段是有意省略业务细节的流程摘录，不是完整 `main` 源码。尤其不要把“调用了一个初始化函数”直接等同于“相应外设已经开始所有业务”：例如初始化定时器寄存器之后，通常还要执行相应 Start 操作才开启所需计数或输出。

本工程的 `HAL_Init()` 配置 Flash 预取、NVIC 优先级分组、默认 1 ms 时间基准，并调用 `HAL_MspInit()` 等底层初始化。随后 `SystemClock_Config()` 才切换应用时钟。

已经核对的配置意图是：

```text
外部 HSE（工程按 8 MHz 假定）
    → 预分频 /1
    → PLL ×9
    → SYSCLK = 72 MHz
    → AHB /1：HCLK = 72 MHz
    → APB1 /2：PCLK1 = 36 MHz
    → APB2 /1：PCLK2 = 72 MHz
```

HSE 启动后要等 `HSERDY`，PLL 启动后要等 `PLLRDY`，再正确切换系统时钟并确认切换状态。提高频率还要匹配 Flash 等待周期；本次传给 `HAL_RCC_ClockConfig` 的参数为 `FLASH_LATENCY_2`。Flash 不会因为 CPU 加速就无限缩短访问时间，等待周期是正常时序配置的一部分。

工程里的 `HSE_VALUE = 8000000` 是软件计算所用的假定，不是芯片自动测量晶振得到的结果。实际板子上必须装有并正常运行符合配置的时钟源，才能据此得到真实的 72 MHz。本文没有测量该板子的实际频率。

`SystemCoreClock` 也只是 RAM 里的一个软件变量。启动时先从 Flash 复制 8,000,000；切换时钟后，由相关软件更新它。给这个变量赋值不会直接改变振荡器频率，真正控制时钟的是 RCC 等硬件寄存器。软件记载与硬件实际不一致，会影响延时、波特率等计算。

当前 HAL 的 `HAL_RCC_ClockConfig()` 在更新 `SystemCoreClock` 后，还会重新调用 `HAL_InitTick(uwTickPrio)`，按新时钟调整时间基准。否则，同一份 SysTick 计数配置在 CPU 从 8 MHz 切到 72 MHz 后，会对应不同的时间长度。初始化顺序因此不只是代码风格问题，它决定各模块对时钟的认识是否一致。

此外，APB 总线频率不总等于定时器输入频率。对本器件相关定时器，APB 预分频不为 1 时，定时器时钟有 ×2 规则；因此 APB1 是 36 MHz，不代表所有挂在 APB1 上的定时器都只用 36 MHz。具体仍按 RM0008 时钟树核算。

**十七、从一条指令到引脚变化：CPU 到底怎样“执行程序”？**

CPU 的 PC 指向下一处执行位置，取指单元获取指令，译码逻辑识别操作，执行单元完成运算、访存或分支。流水线让部分步骤重叠进行，但程序员看到的是由指令控制的状态变化。

本次第一条 `LDR` 就是一个真实例子：它从 Flash 常量池取出函数入口，放进 R0；随后的 `BLX R0` 改变执行流，让 CPU 到 `SystemInit` 处继续取指。

Flash 中的常量池和代码可能相邻，CPU 不会因为字节存放在“代码段附近”就自动判断哪个是变量、哪个是函数。正确的入口和分支让 CPU 只在应该取指的位置执行，并在需要常量时发起数据读取。错误跳入常量区，可能把数据当作指令，进而产生异常。

对 GPIO，下面是一个机制示意：

```c
// 前提：GPIOA 时钟已开启，PA5 已被配置为所需输出模式。
GPIOA->BSRR = 1U << 5;
```

STM32F1 的 GPIOA 基址为 `0x40010800`，BSRR 偏移为 `0x10`。这条语句会被编译成构造地址和值、再写入 `0x40010810` 的指令序列。总线把访问送到 GPIO 外设，外设解释 BSRR 的置位语义，改变输出锁存状态，输出电路才驱动引脚。

这里既不需要 CPU 把 C 文本发送给引脚，也不需要操作系统帮每次写寄存器完成调度。寄存器是软件影响电路的一种约定接口；时钟使能、引脚模式、复用和外部负载决定最终能否得到期望的电平。

在总线层面，Cortex-M3 对代码区有 ICode / DCode 访问路径，对 SRAM 和外设还有系统总线路径。统一地址空间与内部多条总线并不矛盾，也不意味着“代码一定不能放 RAM”。把代码放 RAM 可以实现，但需要正确的链接地址、搬运和执行入口，不会因为复制了文件就自动完成。

**十八、main 运行后，中断为什么能打断它，又怎样回来？**

向量表不仅在复位时有用，后续异常和外设中断也靠它找到处理函数。它的基址由 SCB 的 VTOR 管理；对外设 IRQ，常用的表项地址关系是：

```text
表项地址 = 向量表基址 + 4 × (16 + IRQn)
```

当前正常 Flash 启动场景下，`SystemInit` 没有重定位向量表，因此可以使用复位默认的零地址启动映射。某些工程会显式把 VTOR 设置成 `0x08000000`；若应用被移到别处或向量表复制到 RAM，就必须让 VTOR 与实际布局对应。

这份程序的 SysTick 向量在表偏移 `0x3C`，值为 `0x08003B27`，实际处理指令位于 `0x08003B26`。处理函数调用 `HAL_IncTick()`，推动 HAL 时间基准。

一个普通外设中断能得到执行，通常需要外设产生事件、相应中断源使能、NVIC 对该 IRQ 的使能与优先级允许，并且没有被当前屏蔽或更高优先级执行状态阻挡。SysTick 属于内核异常，其使能方式与普通外设 IRQ 不完全相同。

异常入口会由硬件保存基本现场，包含 R0～R3、R12、LR、PC、xPSR；基本帧为 8 个字，即 32 字节，必要时另有对齐填充。处理函数还可能自行保存其他寄存器。异常返回时，内核利用特殊的异常返回信息恢复现场，使被打断的执行流继续进行。[PM0056 异常模型](https://www.st.com/resource/en/programming_manual/cd00228163.pdf)

所以 `while (1)` 并不等于 CPU 永远只执行循环体中的那几条指令。中断可以在允许的时机插入：

```text
main 主循环 ──→ 被打断 ─────────────────────→ 继续主循环
                    │                       ↑
                    └─ 保存现场 → ISR → 恢复现场
```

`HAL_Delay()` 也不是 HAL 函数自己创造时间。当前工程依赖 SysTick 推动 `uwTick`，延时逻辑等待时间差达到条件。如果在禁止中断的状态下调用它，或者在 SysTick 无法抢占的 ISR 中等待它，就可能等不到需要的计数变化。

此外，中断嵌套和较大的局部数组会消耗栈。即使静态全局变量只占少量 RAM，运行时仍可能栈溢出；这需要栈用量分析或实际观测，不能只靠 BIN 大小判断。

**十九、烧录、调试和独立启动，是三个相关但不同的过程。**

用 ST-LINK 通过 SWD 下载时，工具通过调试访问机制控制芯片，完成 Flash 的擦除、编程和校验。具体下载实现可能把 Flash 编程算法放进 SRAM 中执行。这个过程不能被理解成“用户 main 必须先运行起来，才能把程序写进去”。

通过 ST 出厂 Bootloader 下载则不同：先选择 System memory 启动，再由芯片执行其中的协议程序。本器件所属的中容量 STM32F1 出厂下载通路使用 USART1，常用引脚是 PA9 / TX、PA10 / RX。它有 USB 外设，不等于它的出厂 Bootloader 就支持 USB DFU；要按具体型号查看 [AN2606 系统存储器启动说明](https://www.st.com/resource/en/application_note/an2606-stm32f10xxx-hardware-design-checklist-stmicroelectronics.pdf)。

下载器报告“Verify OK”，通常只说明指定内容写入并校验通过，不自动保证下面这些条件都满足：

- BOOT 引脚选择了用户 Flash；
- 程序写入地址与链接地址一致；
- 工具已执行所需的复位与继续运行操作；
- 时钟、供电和外设电路符合程序要求；
- 程序没有停在断点、错误处理或异常处理函数中。

调试器还可以设置 PC、SP、断点，改变复位方式，或提供半主机服务，因此“在调试模式能跑”不一定完全代表“脱离调试器上电也能跑”。工程若依赖半主机 `printf`，独立运行时还要检查相关处理。本次反汇编中 `fputc` 调用的是 UART 发送函数，不能仅因链接了 `printf` 就说它依赖半主机。

“烧录后必须拔电再插电”也不是这颗单片机正常工作的必然要求。先检查下载后的 reset/run 设置、BOOT 状态以及外设状态。拔电可能同时重置 MCU 之外的 OLED、传感器或驱动器，这种效果与只复位 MCU 不同。

**二十、用户 Bootloader、启动汇编和 ST 出厂 Bootloader，不要混成一件事。**

| 名称 | 通常在哪里 | 负责什么 |
|---|---|---|
| 启动汇编 / `Reset_Handler` | 用户固件的一部分 | 承接硬件复位，建立进入 C 程序的路径 |
| ST 出厂 Bootloader | System memory | 按芯片支持的接口接收下载协议、操作用户 Flash |
| 用户自写 Bootloader | 通常放在用户 Flash 的固定分区 | 决定运行、校验、更新或切换应用程序 |

普通裸机程序可以从 Flash 直接进入自己的 `Reset_Handler`，并不要求先执行一次 ST 的串口 Bootloader。

当前镜像虽然包含 `bootloader_init` 和 `bootloader_process`，但它们是在 `main` 后半段才被调用的。已检查的反汇编显示，前者开启 USART2 的接收到空闲中断流程，后者读取一个接收长度量并打印。不能凭函数名字，就认定这份程序已经具备完整的固件升级、分区校验或应用跳转能力。

如果未来真正采用 Bootloader + App 架构，例如把 App 放在 `0x08004000`，那么至少要让以下三件事一致：

```text
App 链接起点          = 0x08004000
App 实际烧录起点      = 0x08004000
App 自己的向量表起点  = 0x08004000
```

这里的 `0x08004000` 仅是分区示意，不是对当前镜像的修改建议；当前镜像已经大于 16 KiB，不能直接拿它当成这个示例中的 Bootloader 分区内容。

BOOT0 为 0 时，硬件仍先读取 `0x08000000` 处的向量，而不会自动猜测 `0x08004000` 有一个 App。由前面的 Bootloader 决定是否跳过去。

软件跳转还不是硬件复位：外设、SysTick、DMA、NVIC 挂起状态、屏蔽寄存器和运行模式都可能保留。需要根据双方约定清理状态，检查 App 的栈指针和入口，设置适当的 VTOR、MSP，并进入 App 的复位入口，而不是直接调用 App 的 `main()`。App 自己仍需要执行 RAM 初始化。

尤其不要随意在普通 C 函数中改变 MSP 后继续访问原来的局部变量或正常返回。切换栈后的控制流需要与编译器生成的栈操作协调，通常应采用经过验证的交接实现。仅仅把 VTOR 改到新地址，也不会立即改变 PC、执行 App 或自动装载 App 的 MSP。

对 F103 的自定义向量表，遵守芯片包的向量表对齐要求，常见配置要求偏移为 `0x200` 的整数倍。Flash 分区、参数页、擦除粒度也要一起规划，不能只移动一个入口地址。

**二十一、程序不运行时，按启动链逐层定位，比反复重新烧录有效。**

下面的顺序既适合调试器断点，也适合配合示波器、万用表和寄存器窗口检查。每一层都有自己的证据。

| 层次 | 应查看什么 | 能回答的问题 |
|---|---|---|
| 电源与复位 | 所有 VDD/VDDA、地、NRST 波形 | 芯片是否有稳定执行条件，是否一直在复位 |
| 启动选择 | BOOT0、BOOT1 的实际电平 | 当前到底进入用户 Flash 还是其他启动来源 |
| Flash 镜像 | 读回前两个字，与本次镜像比较 | 固件是否烧到了预期位置，向量是否正确 |
| 初始 CPU 状态 | MSP、PC、复位断点 | 是否从正确栈顶和复位入口开始 |
| `Reset_Handler` | 在 `0x08000104` 断点或单步 | 硬件是否已把控制权交给用户启动代码 |
| `SystemInit` / `__main` | 单步观察转移和 RAM | 是否完成预初始化与运行库初始化 |
| `main` | `0x08004B90` 断点 | C 运行环境是否已建立 |
| 时钟配置 | HSERDY、PLLRDY、SWS、Error_Handler | 是否卡在外部晶振、PLL 或切换阶段 |
| 外设与中断 | 时钟使能、GPIO 模式、NVIC、向量表 | 是否初始化了正确的硬件通路 |
| 异常与栈 | HardFault 状态、堆栈中的 PC/LR、SP 边界 | 是否发生非法访问、错误跳转或栈溢出 |

例如，能命中 `main` 开头的断点，就已经证明“硬件取向量 → Reset_Handler → 运行库 → main”这条路径走通了。接下来应把注意力放在具体初始化步骤，而不是继续怀疑 CPU 不认识 BIN。

若停在 HardFault，可进一步读取 SCB 的 CFSR、HFSR，并在相应有效标志成立时参考 BFAR、MMFAR；同时查看异常保存现场中的 PC，定位出错指令。具体寄存器位解释应按 PM0056，不要把故障地址寄存器中任何旧值都当成有效证据。

若板子反复重新开始，可以在较早阶段记录 RCC_CSR 的复位来源标志，例如上电、引脚、软件或看门狗复位。标志可能保留历史状态，读取、保存与清除的顺序也应设计好。

**二十二、用这份文件做一次可复现的“纸上启动”。**

不接开发板，也能沿着文件证据走完以下过程：

1. 解析 HEX 的 `04` 记录，得到基址 `0x08000000`；检查每行校验和。
2. 提取所有数据记录，确认与 BIN 一致，并核对镜像覆盖到 `0x08005A8B`。
3. 读取 BIN 偏移 0 和 4，得到 MSP `0x20000D58` 与复位向量 `0x08000105`。
4. 到 BIN 偏移 `0x104`，看见复位处理的四条指令；到常量池确认两个跳转目标。
5. 到 `SystemInit` 的实际地址，确认这里只做 `BX LR`。
6. 跟随 `__main` 和 `__scatterload`，解出 24 字节复制项与 3,392 字节清零项。
7. 在 MAP 中查 `OLED_DisplayBuf`、栈区和 `SystemCoreClock`，核对 RAM 目标范围。
8. 跟随运行库进入 `main`，确认 HAL、时钟、各外设的调用顺序。
9. 查 SysTick 表项及处理函数，理解主循环里的延时依靠什么推进。

实际硬件调试时，还可以在复位入口和 `main` 前分别停住，观察 `.data`、`.bss` 的变化。不要要求“复位入口看到的 RAM 必须都是随机数”：调试器、上一次运行或复位种类可能让原内容仍在。验证的是启动代码是否按规定复制和清零，而不是观察到哪一种偶然旧值。

本文使用只读 Python 脚本验证了 HEX 校验和、BIN 一致性、向量、运行库初始化表与关键 MAP 符号。自行复现时，应准备同次构建的 BIN、HEX 和 MAP 文件，并按上述步骤核对；另一版本固件的地址与哈希可能不同。

```text

```
